> 詳細・撤去理由は [CONCEPT_v5.ja.md](CONCEPT_v5.ja.md) の「2026-07-31 決定 (v11: 合議の撤去)」を参照。

> 2026-07-02 策定。v2(tmux組織シミュレーション)からのコンセプト刷新。

## 一言で

**異なるベンダーのAI CLI(Claude / Codex / Gemini / Grok)を1つのチームとして編成し、
同じ課題に対する「提案 → 相互レビュー → 投票 → 決定」をターミナルなしで運転できるコックピット。**

役割分担(分業)だけでなく、**合議(deliberation)**を第一級の機能にする。

## なぜこのコンセプトか

### v2の前提が崩れた

- 「会社型の役割分担をtmuxペインで再現する」パターンは、Claude Code公式の
  Subagents / Agent Teams に吸収された。同じ土俵での再実装は公式との消耗戦になる。
- 実運用で通信が失敗する主因は、stdoutの `[TO: name]` regexパース・宛先解決失敗の
  無言破棄・シグナルファイルのレースだった(調査 2026-07-02)。
  エージェント間の自由なメッセージングに依存する設計そのものが失敗の温床。

### 合議 × 異ベンダーは原理的に強い

- 同一モデルをN体並べた多数決は**間違い方が相関する**ため効果が薄い。
  訓練データも癖も異なるベンダー混成では誤りが独立に近づき、
  アンサンブル(self-consistency / multi-agent debate)の精度向上が実際に効く。
- Agent TeamsはClaude内で閉じており、**異ベンダー合議は公式が構造的に提供できない**。
  ここがMAO唯一にして本物の差別化。
- GUI(非ターミナル層向けコックピット)も公式が埋めていない領域。

## コア設計原則

### 1. 民主主義は「プロトコル」であって「会話」ではない

合議の進行はエージェント同士のチャットに任せず、**MAO本体がステートマシンとして執行する**。

```
[課題投入]
   │
   ▼
① PROPOSE   各エージェントに同一課題を一発実行で投げる
   │         (claude -p / codex exec / gemini -p、応答はJSON)
   ▼
② REVIEW    各エージェントに「自分以外の案」を匿名化して渡し、
   │         批評と改善点をJSONで返させる
   ▼
③ REVISE    (任意)自案への批評を受けて各自が改訂
   │
   ▼
④ VOTE      全案(匿名)を提示し、構造化投票を返させる
   │         { ranking: [...], confidence: 0-1, rationale: "...", objections: [...] }
   ▼
⑤ DECIDE    集計(多数決 / 信頼度加重 / 承認投票)
   │         → 採択案 + 少数意見(minority report)をUIに提示
   ▼
[ユーザー承認ゲート] → 実行フェーズへ
```

- 各ステップは**ステートレスな一発実行**。永続ペイン・ペイン間メッセージング・
  完了シグナルのポーリングは不要になる。
- エージェントの応答は**スキーマ検証付きJSON**のみ。自然言語のstdoutパースを全廃。
- PMエージェントは置かない。進行役はコード。LLMは「提案・批評・投票」だけを担う。

### 2. 投票は匿名で行う

LLMには自分および同系統モデルの出力を高評価する自己選好バイアスがある。
REVIEW / VOTE の入力では案を `Proposal A / B / C` にシャッフル・匿名化し、
どのベンダーの案かを伏せる。対応表はMAOだけが保持し、決定後にUIで開示する。

### 3. 少数意見は資産

多数決は「もっともらしい誤り」に収束しうる。敗れた案・反対票の理由(objections)は
捨てずに決定カードに併記する。最終決定権は常にユーザー(操縦士)にあり、
少数案の採用・再合議(devil's advocate指名での再ラウンド)をワンクリックで選べる。

### 4. 合議は高価。使い所を選ぶ

合議はトークン消費が実行エージェント数×ラウンド数倍になる。

| 向く課題 | 向かない課題 |
|---|---|
| 設計判断・アーキテクチャ選定 | 機械的な一括編集 |
| バグの原因仮説の競合検証 | 手順が自明な作業 |
| コードレビュー・セキュリティ観点出し | 単純な情報取得 |
| 仕様が曖昧で解釈が割れる課題 | |

タスク投入UIで **「分業(delegate)」と「合議(deliberate)」をユーザーが明示的に選ぶ**。
デフォルトは分業。合議は2〜3エージェント・最大2ラウンドを既定とし上限をUIで示す。

## 実行アーキテクチャ

### 残すもの / 捨てるもの

| | v2 | v3 |
|---|---|---|
| エージェント間通信 | stdout `[TO:]` regexパース + ファイルシグナル | **廃止**(合議プロトコルはコード、応答はJSON) |
| 永続tmuxペイン | 全エージェント | **原則廃止**(観察用の生ログビューは残す) |
| PMエージェント | ルートノードが配車 | **廃止**(配車はユーザー+プロトコル) |
| マインドマップUI | プロセスの組織図 | **チーム編成エディタ**に転用(誰を合議に呼ぶか/役割コンテキスト) |
| 外部メモリ(project/agent summary) | プロンプト注入 | **継続**(各一発実行のコンテキストに注入) |
| 権限ポリシー(ask/safe-auto/yolo) | | **継続** |
| mao_artifacts | | **継続**(提案・投票・決定の全記録を保存) |

### Claude同士の並列は公式に委譲

Claudeノードの内部分業(調査の並列化など)はSubagents / Agent Teamsに任せる。
MAOはClaudeを「1票を持つ1メンバー」として扱い、内部で何体使うかは関知しない。
他ベンダーも同様(codexが内部で何をしようと、返すのは構造化された1つの提案)。

### 実行フェーズ

合議で採択された案の**実行**は、最適な1エージェントに委任する(通常はClaude)。
実行結果に対して再び軽量な合議(レビュー投票)を挟むかはユーザーが選択。

## UIコンセプト

- **ラウンドテーブル・ビュー**: 合議中、各エージェントの提案カードが円卓状に並ぶ。
  ステータス(起草中/レビュー中/投票済み)がリアルタイムに見える。
- **決定カード**: 採択案・得票・信頼度・少数意見・「再合議」「少数案採用」ボタン。
- **提案の並列diff**: コード提案は side-by-side で比較表示。
- **履歴**: 過去の合議(誰が何に投票したか、どのベンダーが勝ったか)を蓄積。
  「この種の課題はCodexの勝率が高い」等の統計が将来の編成提案の材料になる。

## MVPの切り方

1. **Phase 1 — 単発の合議**: 1つの質問/課題を2〜3のCLIに投げ、
   PROPOSE → VOTE(REVIEWは省略)→ 決定カード表示まで。exec一発実行+JSONのみで成立。
2. **Phase 2 — フルプロトコル**: REVIEW / REVISE ラウンド、匿名化、信頼度加重、再合議。
3. **Phase 3 — 実行接続**: 採択案を実行エージェントに委任し、成果物への
   レビュー投票までをタスクパイプラインとして通す。分業モードとの併用。

## リスクと対策

- **コスト膨張** → ラウンド上限・エージェント数上限をUIで明示。概算トークン表示。
- **多数派の誤収束** → 匿名化・objections必須項目・devil's advocate再ラウンド・人間ゲート。
- **CLI仕様変更(出力形式)** → 各CLIのアダプタ層を1ファイルに隔離し、JSONスキーマ検証で
  破損を即検知(黙って壊れない)。
- **公式の追随**(Anthropicが異ベンダー対応する等) → GUI・履歴統計・日本語UXの
  蓄積で先行を保つ。
