# コンセプト v5 — MAO OS: 「動いているAIたちを、1枚のボードで見て、動かす」

> 2026-07-29 策定。v4(付箋キャンバス)のUXとv3(合議エンジン)を継承しつつ、
> 製品の主語を「連携させるツール」から「**複数の稼働中エージェントを管理するOS**」へ転換する。
> v3 = エンジン正典、v4 = 付箋UXとGTM、v5 = AIOSとしての情報設計・管理面の正典。

## 10語以内の商品説明

**「AIたちの仕事場。ボードで見て、Obsidianに残る」**

英語: *Mission control for your AI agents. Backed by Obsidian.*

## 転換の核心 (v4 → v5)

これまでのMAOは「複数のCLIを**同時連携・連結させる**ためのもの」だった。
v5では優先順位を逆転させる。

> **連携機能 < 管理機能。**
> 複数の動いているエージェントを「見やすく・簡潔に・操作できる」ことが第一級。
> 合議・分業はその上に載る1機能に降格する。

理由:

1. **利用実態**: FigmaやNotionでボードに付箋を貼って複数案件を管理する人は大勢いる。
   人間は「並行する仕事を1枚の盤面で俯瞰する」UIに既に慣れている。
   AIエージェントが常時複数動く時代に必要なのは、新しい概念ではなく
   **既に使われている管理のデザインをエージェントに適用すること**。
2. **競合状況**: 連携・オーケストレーション自体は各社公式(Claude Code Agent Teams /
   Subagents 等)が埋めに来る。しかし「**ベンダー横断で稼働中エージェントを俯瞰・
   操作する管理面(management plane)**」は各社が構造的に作れない(自社CLIで閉じるため)。
   v3の「異ベンダー合議」と同じ論理で、管理面こそ中立プレイヤーの領域。
3. **ペイン実感**: エージェントを3体以上動かすと、ターミナルのタブ切替と
   「今どれが何をしてるか分からない」が最大の苦痛になる。連携が失敗する前に、
   まず**可視性**が破綻する。

> **2026-07-29 追記**: エージェント間の紐付け(root/edge/階層dispatch)は廃止した。
> ボード上のノードは自由配置のカードのままだが、線を引く・rootに設定する操作は無い。
> 実行は選択中の1体に単独で実行させるモデルに一本化する(合議は後日 v11 で撤去)。
> これは上記「連携機能 < 管理機能」の転換をUIレベルまで徹底した結果。

> **2026-07-29 決定 (v6)**: 「案件ごとにボードを切り替える」モデルを廃止し、
> **1枚のマップに全エージェントが常に見えていて、プロジェクトごとに"囲い"(フレーム)で
> グルーピングされる**モデルに変更した。Figma の Section / Miro の Frame と同じパターン。

## OSメタファー (AIOSの定義)

「AIOS」を曖昧なバズワードにしないため、OSの構成要素に1対1で対応させる:

| OSの概念 | MAO OSでの対応物 | 実体 |
|---|---|---|
| プロセス | 稼働中エージェント | tmux window + PTY (既存) |
| ファイルシステム | **Obsidian vault** | Markdown + frontmatter (v5で正典化) |
| ウィンドウマネージャ | **ボード** (案件ごとのキャンバス) | React Flow (既存転用) |
| タスクマネージャ | エージェントカード + Attention Inbox | v5新規 |
| 割り込み (interrupt) | 承認リクエスト・エラー・完了通知 | permission bridge (既存) + バッジ化 |
| デーモン | スケジュール実行 (将来) | v5.x |
| IPC | (廃止 — dispatch は v5、合議は v11 で撤去。現在は単独実行のみ) | - |

## バックエンド: Obsidian vault を Single Source of Truth にする

### 現状の問題

- 正典データは `~/.multi-agent-orchestrator/workspaces/default/*.json`(サイロ)。
  Obsidian vault は「agent が読める副次メモリ」に過ぎず、**書き捨てで構造が汚い**。
- vault は agent ごとに設定するため、同じ組織でも書き込み先が割れる。

### v5の設計: vault-first

vault を **workspace 単位で1つ** 設定し(agent 単位設定は互換のため残すが非推奨)、
アプリの永続データを人間が読める Markdown + frontmatter として vault に置く。

```text
Obsidian Vault/
  MAO/
    Home.md                  # ダッシュボード: 全ボード・全エージェントへのリンク (MAOが自動生成)
    Agents/
      <agent>.md             # frontmatter = エージェント設定 (name/type/command/policy/cwd)
                             # 本文 = systemPrompt・役割メモ (人間が編集してよい)
    Boards/
      <board>/
        Board.md             # frontmatter = ボード設定 (workingDirectory, 参加agent)
                             # 本文 = 案件サマリ (= 旧 project_summary.md)
        Notes/<note>.md      # 付箋 1枚 = 1ファイル (frontmatter: status/assigned/position)
        Tasks/<taskId>.md    # タスク仕様と完了報告 (既存 tasks/ を移設)
    Runs/
      <date>/<agent>-<taskId>.md   # 実行ログの要約 (agent_history の可読版)
```

原則:

- **すべて `[[wikilink]]` で接続する**。Task → Note → Agent が
  Obsidianのグラフビューでそのまま「仕事の履歴グラフ」になる。盤面が議事録(v4)
  から一歩進んで、**vaultが会社の記憶**になる。
- **frontmatter は zod で検証**。壊れていたら該当ファイルだけ無視して警告
  (既存JSONの「不正なら空配列」より粒度を細かく)。
- 人間が Obsidian 側で編集 → MAO が **chokidar で watch して反映**(双方向同期)。
  エージェント設定の変更・付箋の追記が Obsidian からでもできる。
- 既存 `agents.json` / `graph.json` / `notes.json` は**キャッシュ兼フォールバック**に
  降格。vault 未設定ユーザーは従来どおり動く(vault はオプトイン、ただし
  オンボーディングで強く推奨)。
- 初回 vault 設定時に既存JSONから**一括マイグレーション**を実行する。

### 同期の規律 (レース対策)

- 書き込みは MAO 側を master とする **last-write-wins + 世代番号**(frontmatter に
  `maoRev: n`)。watcher が自分の書き込みを拾って無限ループしないよう、
  書き込み直後 500ms は該当パスのイベントを無視する。
- エージェント本人による vault 直接書き込みは従来どおり許可(+ sandbox 環境向けの
  `.mao/obsidian_outbox/` 経由インポートも継続)。

## フロントエンド: ボード型エージェント管理

### 画面構成 (Notion/Figmaの慣習に寄せる)

> **2026-07-29 決定**: 現行のビジュアルデザイン(brand-*トークン、フルスクリーン
> キャンバス+フローティングパネル)は維持する。下図のような恒久ドッキング列は
> 採用せず、サイドバーは**左端の折りたたみ式フローティングレール**、Attention Inbox
> は**右下のピル+ポップオーバー**として実装済み(Phase 1 実装 2026-07-29)。

```
┌──────────┬──────────────────────────────┬─────────┐
│ サイドバー │  ボード (React Flow キャンバス)    │ Inspector│
│          │                              │ (選択時) │
│ ▸ Home   │  [付箋] [付箋]   [決定カード]     │         │
│ ▾ Boards │                              │         │
│   案件A ● │  ┌エージェントカード┐              │         │
│   案件B   │  │ 🤖 Claude/実装  │              │         │
│   案件C ⚠ │  │ ▶ running 3:12 │              │         │
│ ▸ Agents │  │ "APIのテスト修正中"│             │         │
│          │  └───────────────┘              │         │
├──────────┴──────────────────────────────┴─────────┤
│ Attention Inbox (⚠2)          │ Terminal (折りたたみ)  │
└───────────────────────────────────────────────────┘
```

1. **サイドバー = プロジェクト(囲い)の一覧**。ただし v4/v5初期の「ボード切替」とは違い、
   キャンバスは常に1枚。行をクリックすると**その囲いへパン/ズームするだけ**で、表示の
   切替(他のプロジェクトが見えなくなる)は起きない。プロジェクト = 1囲い = 1 folderPath。
   行の右に稼働ドット(●=running数)と⚠(要対応)を常時表示。
   **一覧常駐 + 移動**にするのは「今どれが動いてるか」を見失わせないため。
2. **エージェントカード = 生きているプロセス表示**。v4の「メンバーカード」を
   タスクマネージャに進化させる:
   - 状態リング(v4のnode glowを継承: 黄=starting / シアン=running / 赤=error)
   - **今やっていること1行**(PTY出力の末尾から抽出、3秒スロットル)
   - 経過時間・当該ボードでの実行回数
   - ホバーで操作: `⏸ 中断` `⏹ 停止` `⌨ ターミナル` `📄 直近ログ`
   - ⚠バッジ = 承認待ち(クリックでその場で許可/拒否 — 既存 PermissionDialog を
     カード内ポップオーバーに移植)
3. **Attention Inbox (v5の目玉)**。全ボード横断で「人間の判断が要るもの」だけを
   時系列に集約: 承認リクエスト / エラー / 完了報告 / cwd変更。
   各項目はワンクリックで該当ボード・該当カードへジャンプ。
   **「MAOを開いたらまずここだけ見れば良い」**という契約を作る。
4. **付箋は v4 のまま**(貼る/渡す。「会議にかける」は v11 で撤去)。付箋の保存先が
   `notes.json` から vault の `Notes/*.md` に変わるだけで操作は不変。
5. **ターミナルは既定で閉じる**(v4方針を継続)。カードの `⌨` から該当 tmux window
   を直接開く動線に一本化。

### 操作の動詞 (v4の2つ + 管理の3つ。「会議にかける」は v11 で撤去)

| 動詞 | 操作 | 由来 |
|---|---|---|
| 貼る | 付箋を置く | v4 |
| 渡す | 付箋をカードへドラッグ | v4 |
| **見る** | サイドバー・カード・Inboxを眺める (操作ゼロで状況把握) | v5 |
| **応える** | Inboxで承認/拒否/再実行 | v5 |
| **束ねる** | エージェントを囲い(プロジェクト)にドラッグして入れる | v6 |

## 実装方針 (3案比較)

- **A. 既存Electronアプリを段階改修**(採用)— React Flow・tmux/ttyd・
  permission bridge を全部活かす(合議エンジンは v11 で撤去済み)。vault-first 化は
  ストレージ層の差し替えで、UIは AgentCard / Sidebar / AttentionInbox の追加が主。
- B. Obsidianプラグインとして作り直す — 「バックがObsidian」を最も純粋に実現するが、
  PTY/tmux/権限ブリッジをObsidianのsandboxで動かすのは無理筋。CLI実行という
  製品の芯が成立しない。**却下**(ただし将来「閲覧専用Obsidianプラグイン」は
  vault が正典化されていれば無料で手に入る — vault-first の副次効果)。
- C. Web化・SaaS化 — v4で却下済みの理由がそのまま生きる。**却下**。

## バグが出やすい箇所 (先回り指摘)

1. **chokidar の自己ループ** — MAOの書き込みをwatcherが拾い、再保存→再通知の無限
   ループ。書き込みパスの一時ミュート+maoRev比較の二段構えで防ぐ。テスト必須。
2. **「今やっていること1行」の抽出** — PTYはANSIまみれ+各CLIで形式が違う。
   stripAnsi後の末尾非空行をそのまま出す素朴実装から始め、CLI別の整形は後回し。
   凝ったパースは v2 の stdout regex 地獄の再来になる(v3の教訓)。
3. **複数プロジェクト(囲い) × tmux** — 現在 tmux session は `mao-orch` 1本、window は
   agentId 単位。囲いはあくまで「所属の見た目とcwdの初期値」を決めるだけで、実行中の
   tmux window / PTY はエージェント単位のまま変わらないため、v4時代のボード切替のような
   session/window 衝突は起きない。ただし囲いを跨いでエージェントを移動させても、
   稼働中の PTY の cwd はその場では変わらない(次回起動から反映)点は注意が必要。
4. **frontmatter手編集の破壊** — 人間がObsidianでYAMLを壊すのは日常。zodで
   ファイル単位に隔離し、「このファイルを無視しています」をUIに出す(黙殺しない)。
5. **Inboxの通知洪水** — 完了報告まで全部入れると即座に形骸化する。既定は
   「人間の判断が要るもの」のみ、完了は折りたたみ。通知の格付けを最初に決める。
6. **iCloud/Dropbox上のvault** — 同期アプリとchokidarの相性問題(部分書き込み検知)。
   書き込みはtmp→renameのatomic writeで行う。

## テスト観点

- vault同期: MAO書込→Obsidian編集→MAO書込の交互更新 / YAML破壊 / vault削除・移動 /
  iCloud同期遅延中の読み書き。
- ボード: ボード追加・削除・切替時の稼働agentの継続性(切替でPTYが死なないこと)。
- Inbox: 承認をInboxから応答 / カードから応答 / 両方開いた状態の二重応答。
- 移行: 既存JSONのみ→vault設定→一括移行→JSONフォールバックの各系。
- 後方互換: vault未設定ユーザーがv4と同一の挙動を得ること。
